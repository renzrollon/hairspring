# Glossary

Working definitions of the terms the skills use, written in our own words. Each term is also a term in the public IREB CPRE Glossary (v2.2); see the IREB glossary for the authoritative definitions. re-skills is independent of IREB and not endorsed by it.

| Term | How re-skills uses it |
| --- | --- |
| Acceptance criterion | A condition, stated so it can be checked, that an implementation must meet for a requirement (often a user story) to be accepted. In re-skills: `R-nnn.ACn`, Given/When/Then. |
| Attribute | A named property recorded for every requirement (ID, type, source, priority, status, rationale, ...). Defined in `requirements/schema.json`. |
| Baseline | A named, frozen snapshot of a set of requirements and their versions, used as a reference point for comparison and contracts. |
| Change request | A formal request to change agreed requirements, assessed for impact before a decision. In re-skills: `CR-nnn`. |
| Conflict | A situation where stakeholders, sources or requirements cannot all be satisfied as stated. In re-skills: `CF-nn`. |
| Constraint | A requirement that limits the solution space without being a function or a quality, because someone outside the team mandates it (law, platform, contract, organization). Type `C`. |
| Context boundary | The line between the parts of the environment that matter to the system and those that do not. |
| Elicitation | Finding, drawing out and refining requirements from stakeholders, documents and systems. |
| Functional requirement | A requirement about a result or behavior the system shall provide. Type `F`. |
| Glossary | The project's agreed list of terms and their meanings; in re-skills `requirements/glossary.md`. |
| Kano model | A way to classify requirements by their effect on satisfaction: dissatisfiers (basic), satisfiers (performance), delighters (excitement). |
| Quality requirement | A requirement about a quality the system shall have (performance, reliability, security, usability, ...), not covered by functional requirements. Type `Q`. |
| Requirement | A need perceived by a stakeholder, or a capability or property a system shall have, documented so it can be agreed and verified. |
| Requirements source | Where a requirement comes from: a stakeholder, a document or a system in operation. In re-skills: `S-nn`. |
| Stakeholder | A person or organization that has an interest in, or influence on, the system's requirements. In re-skills: `SH-nn`. |
| System boundary | The line between the system under development and its context: what we build versus what we interact with. |
| System context | The part of the environment relevant to defining and understanding the system's requirements. |
| Traceability | The ability to follow a requirement back to its source and forward to its design, code and tests, and to related requirements. |
| Validation (of requirements) | Checking that documented requirements are adequate: that they express the stakeholders' actual needs and meet the quality criteria. |
| Verification | Checking that an implementation meets its requirements (test, inspection, analysis, demonstration). |
| Work product | A recorded intermediate or final result of requirements engineering work (a context diagram, a requirements register, a review report). |
