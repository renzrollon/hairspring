## How this skill applies the practice

- Treats verifiability as a property every requirement must have before it is agreed, and checks it row by row rather than leaving it to test planning.
- Records for each requirement how it will be shown to be met (test, inspection, analysis, demonstration), so the effort and the evidence are known early.
- Writes acceptance criteria as pass/fail statements with explicit boundaries, so different testers reach the same verdict.
- Separates the form of a measurable criterion from its values: the skill proposes the form, while targets come only from stakeholders or registers, and unknown values stay visible as TBD with a question.
- Feeds the verification method back into the register (`Verification` column), which the Definition of Ready and the QA view rely on.

## What this skill deliberately leaves out

- Writing Given/When/Then acceptance criteria for user stories: `user-story-refiner`.
- Eliciting quality targets with stakeholders: `quality-requirements`, `clarifying-questions`.
- Linking requirements to existing tests and reporting coverage: `traceability-matrix`.
