## How this skill applies the practice

- Treats the RE process as something to configure per project, not a fixed recipe: three facet choices plus the criticality of the system decide how much is written down and when.
- Decides at the start which work products the team will keep, so each later skill knows whether its file is expected, deferred with a trigger, or skipped.
- Ties the change authority to the facets: a signed, prescriptive scope needs a board and change requests, while an iterative internal team lets the product owner decide.
- Fixes the ID scheme and the minimum attribute set once, so every requirement carries its source, priority and rationale from the first row.
- Writes a Definition of Ready that grows with the facets instead of a generic checklist.

## What this skill deliberately leaves out

- Designing extra attributes, lifecycle states and audience views: `attribute-schema`.
- Running the change process itself: `change-impact`.
- Choosing elicitation techniques per source: `source-inventory`.
