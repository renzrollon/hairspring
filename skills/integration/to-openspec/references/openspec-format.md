# OpenSpec format targeted by `to-openspec`

**Checked:** 2026-11-03, against OpenSpec **1.16.0** (`@fission-ai/openspec` on npm; repository `Fission-AI/OpenSpec`, commit `2bd5bc3`, 2026-11-02). The example in `examples/` was validated with `openspec validate add-voucher-redemption --strict` on that version.

**Sources** (re-check them when OpenSpec changes major or minor version):

- Default workflow schema and its templates, the authoritative format: <https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml> and <https://github.com/Fission-AI/OpenSpec/tree/main/schemas/spec-driven/templates>
- Concepts (folders, delta specs, archive): <https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md>
- Writing specs (requirements, scenarios, RFC 2119 keywords): <https://github.com/Fission-AI/OpenSpec/blob/main/docs/writing-specs.md>
- CLI (`validate`, `--strict`): <https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md>
- Validator limits and messages: `src/core/validation/constants.ts`, `src/core/parsers/requirement-text.ts`, `src/core/change-metadata/schema.ts` in the same repository.

At 1.16.0 the repository has no `docs/AGENTS.md`; agent instructions are generated per tool by `openspec init` from the schema above, so the schema is the reference.

## Folder

```text
openspec/
  config.yaml                       project config (`schema: spec-driven`); written by `openspec init`, never by to-openspec
  specs/<capability>/spec.md        source of truth; written by `openspec archive`, never by to-openspec
  changes/<change>/
    .openspec.yaml                  change metadata
    proposal.md                     why, what changes, capabilities, impact (+ re-skills sections)
    tasks.md                        implementation checklist
    specs/<capability>/spec.md      one delta spec per capability
    design.md                       optional; written by the implementer, not by to-openspec
```

- `<change>`: kebab-case, verb-led (`add-voucher-redemption`). One intent per change.
- `<capability>`: kebab-case path for a durable behavior (`voucher-redemption`, or `loyalty/voucher-redemption` if the project nests by domain). Reuse the exact existing path when `openspec/specs/<capability>/` exists.
- A `spec.md` directly under `changes/<change>/specs/` (no capability folder) is an error.

## `.openspec.yaml`

```yaml
schema: spec-driven
created: 2026-11-03
x-re-skills-source: requirements/requirements.csv
x-re-skills-ids: [R-040, R-041, R-042, R-085, R-100]
```

`schema` is required when the file exists; `created` is `YYYY-MM-DD`. OpenSpec ignores keys it does not know, and documents `x-*` keys as the place for your own metadata.

## `proposal.md`

OpenSpec parses two sections and ignores the rest:

| Section | Rule | re-skills content |
| --- | --- | --- |
| `## Why` | required; 50 to 1,000 characters (archive warns outside that range) | one or two sentences confirmed by the user; the generated draft joins the rationales of the selected rows |
| `## What Changes` | required; not empty | one bullet per functional requirement: `- <R-ID> <Title> (<Priority>)` |

Sections from the `spec-driven` template, kept: `## Capabilities` with `### New Capabilities` and `### Modified Capabilities` (bullets `` - `<capability>`: <what it covers> ``), `## Impact`.

Sections re-skills adds (ignored by the OpenSpec parser, read by people and agents):

- `## Constraints and Quality Requirements`: table `ID | Type | Requirement | Source | Verification` with every Q and C row, text verbatim.
- `## Not in this change`: table `ID | Reason` for every row left out by the gate (status, lint error, `TBD`, no scenario source), and approvals given by ID.
- `## Traceability`: table `ID | Type | Priority | Status | Source | Lands in` for every row that went across.

Archive warns when a change holds more than 10 requirement deltas; split larger hand-offs into several changes.

## Delta spec: `specs/<capability>/spec.md`

```markdown
# Spec Delta: <capability>

<!-- Generated by re-skills to-openspec ... -->

## Purpose

<New capabilities only: one or two sentences, at least 50 characters.>

## ADDED Requirements

### Requirement: R-040 Issue voucher on redemption request
<!-- R-040 -->
WHEN a member ... the loyalty service SHALL issue ...

#### Scenario: R-040.AC1 The member requests a voucher for 1,000 points
- **GIVEN** a member with 1,250 posted points
- **WHEN** the member requests a voucher for 1,000 points in the customer mobile app
- **THEN** the loyalty service issues a voucher worth SGD 10 and the member's posted balance is 250 points
```

Rules the validator applies (1.16.0):

| Rule | Level |
| --- | --- |
| Delta headers are exactly `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements`, `## RENAMED Requirements` | error if a change has no delta at all |
| Requirement headers are `### Requirement: <name>`; other `###` headers inside a delta section are ignored | silent |
| Every ADDED or MODIFIED requirement has at least one `#### Scenario:` (exactly four `#`) with a non-empty body | error |
| A scenario has a `WHEN` or `GIVEN` step and a `THEN` step (bold `**WHEN**` or bare upper-case `WHEN`); `AND` only continues a step | warning; fails `--strict` |
| The requirement text (between the header and the first scenario) contains upper-case `SHALL` or `MUST` | warning; fails `--strict` |
| The requirement text is at most 500 characters, including the `<!-- R-nnn -->` line | warning; fails `--strict` |
| `## Purpose` for a new capability is at least 50 characters and not a `TBD` placeholder | warning; fails `--strict` |
| `## Purpose` in a delta for an existing capability | ignored |

Which delta section a row goes to:

- **ADDED**: the R-ID does not appear in any `openspec/specs/**/spec.md`.
- **MODIFIED**: the R-ID's anchor already exists in `openspec/specs/<capability>/spec.md`. Copy that requirement's header text exactly (whitespace-insensitive match), write the full new block including every scenario, and omit `## Purpose`.
- **REMOVED**: not generated in this version. If a withdrawn R-ID still exists in `openspec/specs/`, list it in the final message; the user writes the `## REMOVED Requirements` block by hand with `**Reason**:` (the Rationale) and `**Migration**:` lines.

## Mapping from the register

| Register | OpenSpec |
| --- | --- |
| Row with `Type=F` | `### Requirement:` block in the capability's delta spec |
| Row with `Type=Q` or `Type=C` | `proposal.md` → "Constraints and Quality Requirements"; `tasks.md` group "Quality requirements and constraints" |
| `ID` | first token of the requirement name; `<!-- R-nnn -->` on the line after the header; first token of scenario names; last token of task lines `(R-nnn)` |
| `Title`, else the first 8 words of `Text` | rest of the requirement name |
| `Text` | requirement body, verbatim, except: whole-word `shall` and `must` become `SHALL` and `MUST`; `should` and `may` become `SHOULD` and `MAY` only when the text has no `shall`/`must` |
| Acceptance criterion `R-nnn.ACn` ("Given ..., when ..., then ...") | `#### Scenario: R-nnn.ACn <the When clause: first 8 words, first letter capitalized>`. A clause starts at `Given`, `When`, `Then`, `And` or `But` (any case) at the start of the criterion or right after `, ` or `; `; each clause becomes a `- **GIVEN**`, `- **WHEN**`, `- **THEN**` or `- **AND**` bullet (`But` → `AND`), in order, verbatim without the keyword and the final period. An `and` inside a clause does not split it |
| No acceptance criterion, EARS text | one derived scenario `#### Scenario: R-nnn main case (derived from the requirement text)`. The main clause is the text after `, THEN ` (for `IF`), else after the right-most `, ` whose remainder holds the obligation verb. The condition part splits at the upper-case keywords: `WHERE` and `WHILE` clauses become `**GIVEN**`, `WHEN` and `IF` clauses become `**WHEN**`, the main clause becomes `**THEN**`; all verbatim without the keyword and the final period |
| No acceptance criterion, ubiquitous text | no scenario can be derived; the gate blocks the row |
| `Tags` entry `cap:<name>` | capability folder; without one, the change name minus a leading `add-`, `update-`, `change-`, `remove-` or `fix-` |
| `Verification` (or `verification.csv`) | verification wording in the task line (`verify by test`, `by inspection`, ...); `by test` for F rows when empty |
| `Source`, `Priority`, `Status`, `Rationale` | `proposal.md` → "Traceability"; rationales seed the `## Why` draft |
| Rows left out by the gate | `proposal.md` → "Not in this change" |

## `tasks.md`

```markdown
# Tasks

## 1. <capability>

- [ ] 1.1 Implement R-040 <Title>; verify by an automated test for scenario R-040.AC1 (R-040)

## 2. Quality requirements and constraints

- [ ] 2.1 Verify R-085 <Title> by test against the target in proposal.md (R-085)
```

- Every tracked task is `- [ ] N.M <description>`; a box holding `x` counts as done.
- One numbered group per capability, in the order of the proposal; then one group for quality requirements and constraints.
- Every task states how it is verified, and ends with its R-IDs in parentheses.

## Validation without the CLI

- [ ] `.openspec.yaml` has `schema: spec-driven`.
- [ ] `proposal.md` has `## Why` (50 to 1,000 characters) and a non-empty `## What Changes`.
- [ ] Each capability listed under `## Capabilities` has `specs/<capability>/spec.md`, and each spec file is listed.
- [ ] Each delta spec has a delta header; new capabilities open with `## Purpose` (50 characters or more).
- [ ] Each `### Requirement:` has text with `SHALL` or `MUST`, at most 500 characters, and at least one `#### Scenario:` with a WHEN or GIVEN bullet and a THEN bullet.
- [ ] Every line in `tasks.md` that should be tracked is a `- [ ] N.M` checkbox.

## After the hand-off

- `openspec archive <change>` merges the ADDED and MODIFIED blocks, R-IDs included, into `openspec/specs/` and moves the folder to `openspec/changes/archive/YYYY-MM-DD-<change>/`.
- Quality requirements and constraints stay in the archived `proposal.md`; they are not merged into `openspec/specs/`. `requirements/requirements.csv` remains the register for them.
- Ask the implementer to cite R-IDs in commit messages and test names (`test_r_040_issues_voucher`), so `traceability-matrix` can close the trace from requirement to code and test.
